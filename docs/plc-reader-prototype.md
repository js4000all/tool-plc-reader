# PLC Reader プロトタイプ — Codex向け設計引き継ぎ

## 1. 目的

Go言語によるPLC Readerのプロトタイプを開発する。

PLC Readerは、複数のPLC（TCPサーバ）から定期的にデータを取得し、センサー定義に従って測定値へ変換し、OTLPで後段のOpenTelemetry Collectorに出力するアプリケーションである。

本プロジェクトでは、OpenTelemetry CollectorのカスタムReceiverとして実装する方式ではなく、**独立したGoアプリケーションとして実装する方式**を検討している。

初期目標は以下のとおり。

- 単一バイナリで動作すること
- ローカル設定ファイルから動作定義を読み込むこと
- 複数PLCへのアクセスに対応すること
- Regionごとに指定した周期でデータを取得すること
- デジタル値・アナログ値を処理できること
- デジタル値の変化検出に対応すること
- OTLP形式で後段へ送信できること
- 構造を必要以上に複雑化しないこと

実装言語はGoとする。測定値のOTLP出力にSDKを使うかは、制約を調査したうえで判断する。

## 2. 基本アーキテクチャ

想定する処理の流れは以下。

```text
Configuration
     |
     v
Builder
     |-- Region定義を解決
     |-- センサー定義を解決
     |-- RegionProcessorを生成
     |-- RegionTaskを生成
     |
     v
Scheduler
     |-- 4秒周期
     |     `-- RegionTask: digital
     |
     `-- 60秒周期
           |-- RegionTask: diagnostic
           |-- RegionTask: analog_u16
           |-- RegionTask: analog_s16
           `-- RegionTask: analog_u32

RegionTask
     |
     |-- PLCClient.ReadWords()
     |          |
     |          `-- TCP通信
     |
     |-- RegionProcessor.Process()
     |          |
     |          |-- センサー値抽出
     |          |-- 型変換
     |          |-- 変化検出
     |          `-- 測定値生成
     |
     `-- OTLP Output
               |
               v
        OTel Collector
```

これは論理構造であり、コンポーネントを個別のプロセスとして実装する必要はない。

### 2.1 Builder

設定ファイルを読み込み、起動時に実行構造を構築する。

責務：

- 設定の妥当性検証
- Region定義とセンサー定義の関連付け
- RegionProcessorの構築
- RegionTaskの構築
- SchedulerへのTask登録

センサー定義の解析やアドレス解決は原則として初期化時に行い、周期的な収集処理中に繰り返さない。

Builderは概念上の名称であり、必ずしも独立した型やパッケージとする必要はない。

### 2.2 Scheduler

責務は「いつ、どのTaskの実行を要求するか」。

- Regionごとの収集周期を管理する。
- 同じ周期のRegionTaskをまとめて扱う。
- 周期到来時に各RegionTaskの実行を要求する。
- PLC接続やセンサー定義の詳細は知らない。

**同一周期のTaskをまとめて管理することと、複数Regionを一つのTaskに統合することは別である。**

初期構想では、Taskの単位はあくまでRegionとする。

### 2.3 RegionTask

Regionごとに起動時に生成され、繰り返し実行されるオブジェクト。

責務：

1. 対象Regionのワード列をPLCから取得する。
2. 取得時刻などのメタ情報を付与する。
3. RegionProcessorへ取得データを渡す。
4. 処理結果を出力経路へ受け渡す。

同じRegionTaskの重複実行は禁止する。

前回の実行が完了していない状態で次の周期が到来した場合、原則としてその周期をスキップする。遅延した実行要求を無制限に蓄積しない。

Taskは起動時に生成される実行定義であり、毎周期新しいTaskオブジェクトを生成する必要はない。

### 2.4 PLCClient

PLCとの通信を担当する。

主な機能：

- TCP接続
- 固定I/Fに対するワード単位の読み取り
- タイムアウト
- エラー処理
- 必要に応じた再接続

将来的には同一PLCへの通信直列化や接続再利用を担当する可能性がある。

初期段階では、直列化のための抽象化のみを設け、実装は簡潔に保つ案がある。

ただし、同一TCP接続上で複数要求の送受信が不正に混在しないことは保証する。

### 2.5 RegionProcessor

RegionTaskごとに対応するProcessorを起動時に構築する。

責務：

- 取得したワード列からセンサー値を抽出
- データ型の解釈
- スケーリング
- デジタル値の変化検出
- 測定値の生成

RegionProcessorは、対応する複数のセンサー定義を保持する。

デジタル値の前回値など、処理に必要な状態を保持してよい。

同一RegionTaskの重複実行を禁止し、Processorの状態への並行アクセスを防ぐ方針とする。

初期は同期的な関数呼び出しを想定し、不要なchannelや非同期パイプラインを導入しない。

### 2.6 OTLP Output

Processorで生成した測定結果を後段のOTel Collectorへ送信する。

OpenTelemetry Go SDKの使用を想定しているが、OTLPデータを直接生成する方式も比較対象とする。

詳細は後述する。

## 3. PLC側との共有I/F

PLC内部の実装をReaderから隠蔽しつつ、実装を簡素にするため、PLC側に専用の共有I/F領域を設けることを前提とする。

共有I/Fは、あらかじめ決めたデータ型・用途ごとの連続領域で構成する。Readerはこの領域をバルクで読み取る。

読み取りコマンドは固定化できる見込みだが、通信プロトコルの具体的な仕様は別途確定する。

### 3.1 メモリマップ案

オフセットは共有I/F基点からの16bitワード単位の相対位置とする。

| Offset    | 内容      | 型        | 備考         |
| --------- | ------- | -------- | ---------- |
| 0000–0009 | I/F管理情報 | U16      | バージョン等     |
| 0010–0019 | デジタル値   | Bitfield | 10ワード、160点 |
| 0020–0099 | 異常診断    | S16      | エラーコード等    |
| 0100–0299 | アナログ値   | U16      | 200点       |
| 0300–0499 | アナログ値   | S16      | 200点       |
| 0500–0599 | アナログ値   | U32      | 50点、100ワード |
| 0600–0999 | 予約      | —        | 将来拡張用      |

このレイアウトは現時点の案であり、PLC側との調整により変更する可能性がある。

Region上の位置にセンサーの意味を固定しない。例えば、同じRegion内のoffset 12が何を示すかは、PLCごとのセンサー定義ファイルによって決まる。

RegionSnapshotオブジェクトには、センサー定義ベースで素直に値を取得するためのデコーダーとしての機能も期待する。

### 3.2 I/Fバージョン

共有I/Fの先頭管理領域にI/Fバージョンを格納する。Reader側にも期待するI/Fバージョンを定義し、起動時等に照合する。不一致を早期に検出することが目的。

初期実装では完全一致を要求する方向とする。

Reader自体のソフトウェアバージョンと、共有I/Fのバージョンは区別する。

### 3.3 Region定義

Regionの定義はReaderの設定ファイルに配置する方向。

Regionは少なくとも以下を持つ。

- 識別子
- 共有I/F基点からの相対offset
- ワード長
- データ型

センサー定義は `region名 + offset` で値を参照する。

デジタル値については、Region内の通算bit offsetを使用するか、word offsetとbit offsetを分離するか、別途検討する。

32bit値のワード順序、符号付き値の表現などもI/F仕様として明文化する。

## 4. 収集周期とTaskの関係

初期想定：

- デジタル値：4秒周期
- アナログ値：60秒周期

ただし、周期をこの2種類に固定しない。Regionごとに周期を設定できるようにする。同じ周期のRegionをScheduler内部でまとめて扱い、周期到来時にそれぞれのRegionTaskを起動する。

センサー定義には原則として収集周期を持たせない。したがって、同一Regionに所属するセンサーは同一周期で取得される。この制約は今回のユースケースでは許容できる。

PLCの共有I/F上の論理的なRegion分割と、通信プロトコル上の読み取り要求分割は独立している。例えば、500ワードを1回で取得できない場合でも、必要に応じて複数の通信に分割し、ProcessorにはまとまったRegionSnapshotを渡せるようにする。

## 5. データ処理要件

### 5.1 アナログ値

基本的には、収集周期ごとに取得値を測定データとして出力する。

最低限対応する型：

- 16bit unsigned
- 16bit signed
- 32bit unsigned

スケーリングなどの変換はセンサー定義に基づいて実施する。

### 5.2 デジタル値

基本的には、前回値から変化した場合に出力する。

加えて、長期間変化がない場合も一定周期で値を出力する必要がある。

現時点の想定：

- 収集周期：4秒
- 変化時に出力
- 24時間ごとに再出力

再出力の方法として、以前は「前回値を24時間ごとにリセットする」方式を想定していたが、実装方法は固定していない。
前回値と最終出力時刻を管理し、一定時間経過時に再出力する方式などを比較してよい。

初回取得時の出力、取得失敗時の状態維持、再起動時の扱いも明確にすること。

### 5.3 通信エラー

通信に失敗した場合、取得できなかった測定値を正常な新規測定値として出力しない。

エラーの記録・診断情報の出力を検討する。

PLCごとの障害が他PLCの収集に波及しないことを重視する。

## 6. 並行処理と実行制御

複数PLCと複数Regionに対応するため、独立したTaskの並行実行を認める。

一方、同じRegionTaskの重複実行は禁止する。

これにより、対応するRegionProcessorへの同時アクセスを防ぐ。

検討事項：

- 実行中Taskに対する次回実行要求のスキップ
- タイムアウト
- Scheduler停止時のTaskキャンセル
- エラーが発生したTaskの次周期での再実行
- PLC単位の通信直列化
- 同時TCP接続数の制御

当初はExecutorを設ける構想もあったが、現時点では独立したExecutor/Dispatcherの必要性は確定していない。

**初期候補は、SchedulerからRegionTaskを直接起動し、PLC通信固有の制御をPLCClient側に閉じ込める構成。**

並行度制御が複雑になった場合には、Dispatcher等を追加する余地を残す。

## 7. OTLP出力に関する検討課題

OpenTelemetry Go SDKも選択肢だが、測定データの出力方法には未確定部分がある。

特に、デジタル値の変化履歴を正確な測定時刻とともに送信できるかを検証する必要がある。

要求：

- 個々の測定点の時刻を適切に扱うこと
- デジタル値の変化を失わないこと
- アナログ値を定期的に送信すること
- OTLPで後段のCollectorに連携すること
- 出力障害がPLC読み取りへ与える影響を制御すること

比較対象：

1. OTel Metrics SDKと標準OTLP Exporterを使用
2. OTLPのデータ構造を直接生成して送信
3. 必要なら、Readerの自己監視にSDKを使用し、PLC測定値には別方式を使用

これらを調査し、プロトタイプに適した方式を提案すること。

後段のOTel Collectorにバッチ化や再送などの処理を委ねる方向だが、ReaderとCollector間の障害時動作については別途確認する。

## 8. 設定ファイル

設定ファイルはローカルに配置し、起動時に読み込む。

初期実装では以下は不要。

- リモートからの定義取得
- GitOps的な自動反映
- 設定のホットリロード
- 動的な構成変更

設定ファイルの構造は、概ね以下の要素から構成する。

アプリ設定：

```yaml
tcp:
  timeout: 2s

region_tasks:
  - id: digital
    interval: 4s
  - id: analog_u16
    interval: 60s

otlp:
  endpoint:
    host: localhost
    port: 4317
```

共有I/F定義：

```yaml
plc_common_interface:
  version: 1
  base_address:
    type: DM
    offset: 20000
  regions:
    - id: digital
      offset: 10
      words: 10
      type: bitfield

    - id: analog_u16
      offset: 100
      words: 200
      type: uint16
```

センサー定義：

```yaml
plc_common_interface:
  version: 1

plcs:
  - id: plc01
    host: 192.168.1.10
    port: 8500

sensors:
  - id: motor_running
    plc: plc01
    region: digital
    offset: 37
    mode: on_change

  - id: temperature_in_house
    plc: plc01
    region: analog_u16
    offset: 12
    scale: 0.1
    mode: always
```

これは概念例であり、最終スキーマではない。

複数PLCでRegion定義を共有する方法や、I/F定義とセンサー定義の分割方法はCodexから提案してほしい。

## 9. プロトタイプのスコープ

### 初期実装に含めたい機能

- Go単一バイナリ
- ローカル設定ファイル
- 複数PLC対応
- TCPでのワード読み取り
- I/Fバージョン確認
- Region単位の周期収集
- 同一周期のRegionTaskの管理
- 重複実行防止
- RegionProcessorの事前構築
- デジタル値の変化検出
- アナログ値の定期出力
- OTLP出力
- 通信エラー・タイムアウト
- ローカルレベル単体テストのプロセスの確立

### 初期実装では優先しない機能

- 設定ファイルの動的再読み込み
- リモート設定配布
- 多種類のPLCプロトコル
- 複雑なジョブキュー
- 分散スケジューリング
- 永続化を伴うローカル再送キュー
- 高度な通信接続プール
- 汎用的なPLCデバイスアドレス指定エンジン

## 10. Codexに依頼したい最初の作業

**最初から実装を開始せず、まず実装計画を作成すること。**

計画には次を含めてほしい。

1. 想定アーキテクチャと主要コンポーネント
2. Goのパッケージ構成案
3. 主要な型・インターフェースの定義案
4. 初期化・周期実行・エラー発生時・終了時のシーケンス
5. 設定ファイルのスキーマ案と妥当性検証
6. SchedulerとRegionTaskの並行実行制御
7. PLCClientの通信・接続管理方針
8. OTel SDKとOTLP出力方式の比較
9. テスト戦略とPLCシミュレーターの設計
10. 段階的な実装計画と各段階の完了条件

設計に際しては、以下を重視する。

- Goの標準的な実装スタイル
- シンプルな構造
- 責務の明確さ
- 不必要な抽象化を避けること
- 通信処理とデータ処理の分離
- テスト容易性
- PLCやRegionが増えても破綻しないこと

既存のOSSやGoライブラリを活用できる部分は調査し、必要性を説明すること。

未確定事項については、勝手に仕様を固定せず、推奨案と代替案、判断に必要な情報を示すこと。

特に重要な設計判断は、実装前に確認事項として列挙すること。

最初の成果物は、**レビュー可能な設計・実装計画**とする。
